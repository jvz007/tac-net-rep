# Tec-Tac Framework 1.17.97

Date: 30 October 2026. A disabled module's schedules are paused and hidden by Core. A module that is no longer installed leaves its schedules in the list, marked "Owner module not installed", and an administrator can switch them off or remove them. The two held findings of the 1.17.96 review are fixed.

Closes: Johan's request of 30 October 2026 ("if a module is disable the schedules must be disabled as well, and hidden, if the module is uninstalled then we can disable and remove them"), the Core half of the `reviews/requests/core.md` entry "Scheduler: disable and remove schedules whose owner module is disabled or removed", and the two held findings of the 1.17.96 review (Medium: the rollback warning was too broad; Low: a failed step's output was logged unmasked).

## What changed and why

1. **A disabled module's schedules are paused in bulk and hidden (Scheduler a).**
   * `scheduler.sync_module_schedule_state()` sets `paused_reason` ("paused: module disabled") on every enabled schedule whose `module_id` or `owner_module` is a disabled module, and clears exactly the reason Core set when the module is enabled again. `enabled` and `updated_at` are never written, so a schedule a person switched off stays off and an enabled one runs again exactly as it was.
   * It writes **one audit row per module change** (action `disable` or `enable`, object type `scheduler_module`, metadata `module_id` and `count`), not one per schedule and not one per tick. The per-schedule rows of 1.17.86 are gone. The tick calls it once at its start, and the schedule list calls it too, so the pause and its row never lag the root helper that writes the module state.
   * **Hidden.** `GET /api/tfd/scheduler/schedules/` leaves the schedules of a disabled module out. A detail `GET`, `PATCH` and `DELETE`, and `POST .../run/`, answer 404. `GET /api/tfd/scheduler/runs/` leaves out their runs. The hide reads the module state live at request time, so it does not wait for a tick.
   * **Nothing queued before the disable ever starts.** Run now refuses a paused or hidden schedule (409 `schedule_paused`), `queue_manual_run` refuses it, and the worker (`execute_schedule_run`) ends a queued run `skipped` with a plain reason before any handler runs.
   * **Fail closed.** If the module state cannot be read, nothing is written to the database, module-bound schedules are hidden and skipped, and the list answer carries `module_state_unreadable: true`. Core's own actions (`tec-tac`, `core`) and legacy plugins are never paused or hidden. A module that is not installed is "orphaned" (next item), not "disabled".
   * Enabled modules keep today's rules. A regression test asserts it.
2. **A module that is not installed: "Owner module not installed", Disable and Remove (Scheduler b).**
   * New `installed_module_ids()` (from the module registry, plus `tec-tac`, `core` and legacy plugins). An unreadable registry, or one that lists no module, means every module counts as installed, so nothing is paused as an orphan and nothing destructive is offered on an error.
   * A schedule whose owner module is not installed is paused (`paused: owner module not installed`), never run and never failed, and it stays in the list with three additive fields: `orphaned`, `owner_module_installed` and `orphan_label` ("Owner module not installed"). New filter `GET /api/tfd/scheduler/schedules/?orphaned=true|false`.
   * New routes, Scheduler managers only: `GET /api/tfd/scheduler/orphaned/`, `POST /api/tfd/scheduler/orphaned/<id>/disable/`, `DELETE /api/tfd/scheduler/orphaned/<id>/`, `POST /api/tfd/scheduler/orphaned/modules/<module_id>/disable/` and `DELETE /api/tfd/scheduler/orphaned/modules/<module_id>/` (the two bulk calls need `{"confirm": true}`; the plain Yes or No is the UI's). Each re-checks that the module is still not installed (409 `owner_module_installed`) and the caller's target scope (a row outside it is skipped and counted). A queued or running run answers 409 `active_runs`, with no force. Every call writes a strict audit row first (owner module, owner key, schedule id; the count and the ids for a bulk call). If the row cannot be written, nothing changes (503).
   * **Remove is remembered.** New table `TecTacRemovedSchedule` (migration 0043). `reconcile_schedule` without a person's request for a key an administrator removed creates nothing, logs once and returns `None`. A person's own save in the module (`confirmed_by_request`) recreates it and clears the marker. A schedule that was only disabled returns exactly as it was when the module is installed again.
3. **Held Medium of the 1.17.96 review: the rollback warning is for a timeout only.** `_rollback_verification_step` now needs exit 79, the `[TEC-TAC-INSTALL] VERIFY-FAILED: Verifying <step>` marker and the installer's own `VERIFY STEP FAILED: <step> (timed out after N s ...` line for the same step. No marker, a step that failed without a timeout (a model or RBAC assertion, a route, a registry assertion), a timeout line of another step, and the old installer's exit 1 text are all ROLLBACK FAILED. The "an installer verification step" fallback is deleted. The warning now names what may not have run: `incomplete_stages` (helper scripts, timers, service restart), `restart` (the command) and `advice`. The audit message stays plain. All 12 verification steps run before the service restart, so "timeout only" is the whole rule.
4. **Held Low of the 1.17.96 review: a failed step's output is masked.** `run_verify_step` in `install.sh` no longer runs an unconditional `cat` of the step output. A passing step prints through `scrub_verify_output` (its OK line is still shown, masked). A failing step prints only the masked last 20 lines. Exit codes, the `VERIFY STEP FAILED` line, the `ERROR:` line and the VERIFY-FAILED marker are unchanged.
5. **Text.** `docs/module-scheduling.md` (the 1.17.86 section is rewritten; new "A module that is no longer installed" and "Module developers: a removed schedule is remembered"), `contracts.py` (the `reconcile_schedule` text, the new `removed_owned_schedule` row, the five route rows, the rollback warning text), `docs/system-update-signed-releases.md`. The 1.17.96 release note moved to `docs/releases/`.

## Module-facing changes

Needs `requires.framework >=1.17.97` only where a module calls the new read. Nothing a module calls today changed signature or answer.

* **`reconcile_schedule` for a removed key.** Called WITHOUT `confirmed_by_request` for an `(owner_module, owner_key)` an administrator removed, it creates nothing, logs once and returns `None`. That is the answer it already gave for `enabled=False` when none exists, so no start-up code breaks. A key nobody removed behaves exactly as before. Called WITH `confirmed_by_request` (a person saving it in the module) it creates the schedule and clears the marker. `disable_owned_schedule` and `remove_owned_schedule` called by the module itself clear the marker.
* **New read `scheduler.removed_owned_schedule(owner_module, owner_key)`** returns `{removed_by_administrator: True, removed_at, removed_by_username}` or `None`, so a module can show "removed by an administrator" until a person saves the schedule again. Adoption is optional (`reviews/requests/premium-modules.md` for patchmanagement, Johan's example; `core-modules.md` for the others).
* **Additive schedule fields.** The schedule list and detail answers gain `orphaned`, `owner_module_installed` and `orphan_label`. The list answer gains `module_state_unreadable`. `get_owned_schedule` and the `paused` and `paused_reason` fields are unchanged.
* **Hidden schedules.** The schedules of a disabled module are no longer in the schedule API while it is disabled. Their own module is not running, and they return when it is enabled.
* **A run of a disabled or uninstalled module is skipped before its handler.** A system-action run of a disabled module used to end at the system-action layer with a `caller_unverified` deny row; the worker now stops it first with a skipped run and a plain reason, so no deny row is written for it.
* Checked in `modules/` by `tests/scheduler-compat-1.17.97.py`: 23 modules call `reconcile_schedule`, 8 read `get_owned_schedule`, every keyword they pass is still in the signatures, and no module reads `removed_owned_schedule` yet.
