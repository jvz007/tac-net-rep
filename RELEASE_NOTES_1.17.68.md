# Tec-Tac Framework 1.17.68

Second rebuild of 1.17.68, after the round 1 review and the promotion stop (see "Fixed after review", rounds 1 to 3). Johan signed the patch lockdown (AD-41, "1) signed") and the delegated start (AD-43, CQ204, "3) yes", with AD-42 and AD-44) on 21 October 2026. Both are now ON. The lockdown works only while its conditions hold and does nothing otherwise. The delegated start is live, but nothing calls it yet.

Advanced Patch Management (APM) keeps its decisions: Tactical's own patch policy is switched off while APM is honoured, so an update you set to Ignore stays ignored. A schedule keeps working when the engineer who built it leaves, and the next engineer who edits it takes it over, never with wider reach. Maintenance can start APM's scheduled install with nobody signed in, after a person confirmed it once.

Date: 21 October 2026. One migration (0037). `core.system_actions` goes 1.1.0 to 1.2.0 (additive). New capability `core.patch_lockdown` 1.0.0. Every earlier route, field, signature and refusal reason stays. No new HTTP route.

This is a large release: one migration, three new modules, one new capability and one capability bump. If the reviewer finds it too large, the delegation part (S4) is the piece to split into 1.17.69: nothing else depends on it, and Maintenance's `start_install` stays on its 503 reason until it ships.

**For human review (safety and security).** Section S1 is a named exception to checklist A2 and rule 1.7, which say Core touches Tactical only for authentication and accounts plus the AD-13 and AD-19 paths. Johan signed it on 21 October 2026 (AD-41, "1) signed"). It writes no Tactical data, never overrides an administrator's value, works only while an honoured replacement of Windows Patching is installed, and fails open. Section S4 turns on a run that skips the run-time owner re-check (AD-13 condition 2, CQ50) for one kind of run: a delegated one-off whose signed marker, grant and grant digest still hold (AD-43). Both are rows of `docs/review-accepted-decisions.md` (AD-41 to AD-44).

## What changed and why

Johan's words on 21 October 2026, for each part:

- **S1 (AD-41).** "the tactical patch policy must be disabled when APM is installed so that this doesn't happen." Signed: "1) signed".
- **S2 (AD-42, AD-44).** "If an engieer was responsible to configure APM and leaves the business his account will be disabled, but the work that he has done shouldn't be undone. when an profile is then edited by another engineer the ownership will move to him."
- **S3 and S4 (AD-43).** Signed: "3) yes" (CQ204); "4) yes as built" (CQ205, AD-44). "then let the core and communicator agents build the required contracts. I'll install and test." (Q-APM11, Q-APM12 and patchmanagement 0.12.0.)

1. **S1. Patch lockdown (the former R-36).** New `tec_tac/patch_lockdown.py`. `active()` is True only while a replacement of `patching` is honoured right now (the same source AD-20 uses, cached 30 seconds). A read that fails answers False and logs once, so a fault never switches Tactical's patching off. While active, three guards, none writes Tactical data: (a) at `AppConfig.ready()` in every process Core sets Tactical's own documented `TRMM_DISABLE_APPROVE_UPDATES_TASK` and `TRMM_DISABLE_WINUPDATES_INSTALL_TASK` to True (never to False, never over a value the administrator set); (b) `Agent.approve_updates` is wrapped and returns without approving while active, so Tactical's install call no longer flips an update APM set to Ignore back to Approve (this answers "can Core neutralise the per-endpoint auto-approve inside the install call": yes); (c) the capability `core.patch_lockdown` 1.0.0 answers `status()` = `{active, honoured_module, tasks_off, approve_guard_installed}`. The declared operations a replacement registers and the system actions are not blocked. A guard that cannot install fails open. The Scheduler tick writes one audit row `custom:tactical-patch-lockdown` when the state changes (on, held or off; on and held also say which part is in effect, `tasks_off` and `approve_guard`). For the honoured replacement's install the fixed re-approve warning goes from the confirmation, from `list_actions` and from the audit row (which carries `patch_lockdown: active`) only while the guard is installed in that process. Windows Patching's install keeps the warning. Details: `docs/patch-lockdown.md`.
2. **S2. A schedule keeps the scope it was created with, and ownership moves to the next editor.** Migration 0037 adds `TecTacSchedule.creation_scope` (JSON, default empty). New `tec_tac/scheduler_creation_scope.py`: `capture(user)` stores who, when, the person's Tactical client and site scope and the true role flags. It is stored by `reconcile_schedule` whenever a call carries a person's request and by the browser create and by the owner's edit. It is not stored by `start_one_off_run`, by a module call with no request, or when another person only switches the schedule off. `VerifiedSchedulerRun` gains `has_creation_scope`, `creation_scope_info()`, `held_at_creation(flag)` and `resolved_endpoints(*, whole_scope=False, limit=40000)`. For an unattended run they read the stored record and never the owner's live row, so a disabled owner changes nothing. The endpoints are always the run's targets AND the stored scope. A schedule made before 0037 raises `CreationScopeUnavailable` ("This schedule was made before Core kept its scope. Edit it and save it once."). Core never invents a scope. A `reconcile_schedule` call with a person's request IS an edit: if they are not the stored owner, ownership moves to them after the unchanged checks, with one strict `modify` audit row naming `owner_changed_from`, `owner_changed_to` and `previous_confirmed_by`. **It never widens:** their own scope must cover every target, with no shortcut for a scheduler manager, or the call is refused with "You cannot take over this schedule: some of its targets are outside your Tactical scope." (`TakeoverRefused`; 403 `takeover_out_of_scope` from the browser), nothing changes, and one deny row is written (CQ205, option a). The browser edit moves ownership when another person changes an edit field or switches the schedule on. A rename alone and switching it off move nothing.
3. **S3. The module-owned target resolver.** New `tec_tac/scheduler_target_resolvers.py`: `register_target_resolver(module_id, target_type, resolver)`. The caller is verified from the call stack; the type may not be a type Core reads itself and must be in `target_types` of one of the module's scheduled actions; a different resolver under the same key is refused. Core turns every returned id into a Tactical agent number, checks it exists, and treats a bad, missing or ambiguous id, more than 40000 ids, a non-list and any exception as unresolved. Wiring: system action creation and run read a module-owned type through it; a scoped person may create a resolver-backed schedule when every resolved endpoint is in their own scope (before, a module-owned type needed unrestricted scope). A type with no resolver keeps the old rule. No HTTP route.
4. **S4. Delegation: Maintenance starts APM's scheduled install.** `core.system_actions` 1.2.0: `register_system_action(..., delegable_to=())` and five caller-verified functions, `describe_delegation`, `register_delegation_grant`, `remove_delegation_grant`, `issue_delegation_ticket` and `start_delegated_run`. A person confirms once when they save a Maintenance profile (the plain Yes or No, with its own id prefix, valid 600 seconds). Core stores a grant (`TecTacDelegationGrant`, migration 0037) with the confirmed action, targets and parameters, the person and their scope. Maintenance's live Scheduler run gets a signed 24 hour ticket bound to the run and to the grant's digest. APM presents it to `start_delegated_run`, which re-reads everything, requires every endpoint to be in the grant's targets AND the person's stored scope, and creates APM's own one-off run. APM's handler calls the unchanged `run_system_action`. The one-off is exempt from the owner re-check only while its marker (signed for that very schedule) verifies and its grant is unchanged. Editing, re-saving, switching off or removing the grant revokes every ticket. The same ticket and endpoints never start a second install. One strict audit row per grant and per delegated run, one deny row per refusal, no endpoint ids. At most 20 grants per owner module. `wrong_module` of `run_system_action` is unchanged. It is on in Core (AD-43). Nothing calls it until a signed Maintenance release uses it and a signed APM release switches `start_install` on. The Yes/No text says what really happens: the module starts it later with nobody signed in; Core checks at run time that the confirmation is unchanged, that the modules are on, that the replacement is still honoured and that every endpoint is inside the confirmed targets and the stored scope; Core does not look at the account again, so the run goes on if the account is later disabled; editing or removing the profile stops it.
5. **S5. The registration statement.** Documentation and contract text only: an honoured replacement registers Tactical operations and row lookups under its own module id; Core re-reads the honoured state on every call; enabling the replacement reloads the web workers and restarts Celery, so no extra restart by hand; when it stops being honoured its operations answer 404 `tactical_operation_not_found`. No behaviour changed. Pinned by `tests/replacement-registration-statement-1.17.68.py`.

Closes (`reviews/requests/core.md`): the target-resolver entry, "say how Maintenance's unattended patch step may start APM's scheduled install", "switch Tactical's own patch policy off while APM is installed (R-36)", "creation-time scope read (Q-APM12 b)", and "confirm that an honoured replacement registers under its own module id". The Scheduler progress-call entry stays.

## Module-facing

**Two behaviours are now live (heading for module developers).**

- **While Advanced Patch Management is honoured, Tactical's own approve is inert.** `Agent.approve_updates` returns without approving. So `patchmanagement`'s install no longer re-approves an update set to Ignore, and its confirmation drops the re-approve warning (only while the guard is installed in that process). Windows Patching's own install keeps the warning. `core.patch_lockdown.status()` is unchanged.
- **The delegated start is live, and nothing calls it yet.** A delegated one-off is exempt from the run-time owner re-check only while its marker, grant, grant digest and provider module hold. No module in `modules/` calls `describe_delegation`, `register_delegation_grant`, `issue_delegation_ticket` or `start_delegated_run`. Switching it on makes the weakness named in `reviews/core/BACKLOG-new-findings.md` reachable once a module does: the public delegation functions trust the caller string passed as an argument (Medium, hardening batch H1). That batch is not in this release.

Needs framework 1.17.68. Every addition is a trailing optional keyword, a new method, a new function or a new class. Two behaviours change and are named here.

- **Behaviour change 1: `reconcile_schedule` with a person's request now moves ownership and stores the scope.** Only patchmanagement 0.12.0 (unsigned) passes `confirmed_by_request`; the other 16 callers pass none and are unaffected. A module that passes a request must only do so when a person really saves something. A narrower person is refused with `TakeoverRefused` (a `SchedulerNotAllowed`). The signature and every earlier refusal stay.
- **Behaviour change 2: a module-owned target type with a registered resolver is judged by its endpoints.** Before, it needed unrestricted scope. No module registers a resolver yet.
- **`VerifiedSchedulerRun`.** Two private defaulted fields and four public reads, appended. `has_tactical_permission` and `resource_context` are unchanged and still read the owner fresh. A module that keeps calling them for an unattended run keeps the old behaviour (a disabled owner fails closed) until it adopts the new reads.
- **`core.system_actions` 1.2.0.** Four earlier operations first and unchanged; five appended. `register_system_action` takes `delegable_to` last. `list_actions` rows gain `delegable_to`. The refusal reasons of `run_system_action` are unchanged; the delegation functions raise `DelegationRefused` with its own reasons.
- **New classes and functions.** `CreationScopeUnavailable`, `TakeoverRefused` (in `tec_tac.scheduler`), `DelegationRefused` (in `tec_tac.delegation`), `register_target_resolver` (in `tec_tac.scheduler_target_resolvers`), `status` (in `tec_tac.patch_lockdown`).
- **New capability** `core.patch_lockdown` 1.0.0 with one operation, `status`. A replacement may drop its own "does not apply APM decisions" warning when `active` and `approve_guard_installed` are both True.
- **Audit.** The lockdown row has three states and, for `on` and `held`, the booleans `tasks_off` and `approve_guard`. New rows: `add`, `modify` and `delete` of `delegation_grant` (strict); `add` of `scheduler_run` for a delegated run (strict); `deny` rows with `requested_by: delegation` or `takeover_out_of_scope`; `custom:tactical-patch-lockdown` (non-strict). A `modify` row of a schedule gains `owner_changed_from`, `owner_changed_to` and `previous_confirmed_by` when ownership moved.
- **Contract rows.** New: `describe_delegation`, `register_delegation_grant`, `remove_delegation_grant`, `issue_delegation_ticket`, `start_delegated_run`, `DelegationRefused`, `register_target_resolver`, `CreationScopeUnavailable`, `TakeoverRefused`, `status` (patch lockdown). Updated: `register_system_action`, `reconcile_schedule`, `verify_run_context`, `VerifiedSchedulerRun`, `register_tactical_operation`, `register_tactical_row_lookup`, the confirmation route notes and the system-actions rule.
