## What changed and why

1. **The sweep judges a stored row's `tree_sha256_file` by the registration rule** (held finding, Low).
   * `_sweep_reasons` now calls `_check_relative` on the stored value, next to the check on the runtime path. A value that is not text, is empty, absolute, holds a backslash or NUL, is over 512 characters, or has an empty, `.` or `..` part gives the fixed `unsafe_path` sentence for that root. The listing file is not opened and the runtime folder is not walked. The other roots of the same row are still judged. A valid stored row behaves as before.
2. **The helper's launch path** (`scripts/sandbox-helper.py`).
   * `--start` (sudo, Tactical account): while the switch is off it still refuses with the `sandbox_disabled` frame before it reads stdin. When on, it reads one JSON header line (`runner_id`, `run_id`, `person`, `parameters`, `credentials` as base64, `input_bytes`) and then exactly that many input bytes (capped by `input_kib`). It re-reads the root registry row: registered by a module manifest, `runtime_verified`, runtime roots still root-owned with no writable parent, runner program root-owned, inside its own folder and unchanged (SHA-256). It checks `status.json` is ready, validates the parameters against the registered schema (enum, integer range, string length and pattern; the program is exec'd, never a shell), and checks credential names against `credential_files` and 16 KiB each.
   * **Slots.** Server slots are `min(6, floor((MemAvailable - 1.5 GiB) / memory_max))`, at least 1, as `flock`ed files under `/run/tec-tac/sandbox/slots/`. Per person: 2, with a file name that is a hash of the person. A start waits up to `queue_seconds`, then answers `busy` or `person_busy` with `retry_after` 5. A crash of the helper closes the descriptors, so no slot is left behind.
   * **Credentials** are written only to `/run/tec-tac/sandbox/secrets/<run id>/` (folder 0700, files 0600, root), passed with `LoadCredential`, removed by `ExecStartPost=+/bin/rm -rf`, again in `finally` (success, failure, cancel, exception), and by `--sweep`. Never in argv, the helper's environment, an audit row or a log.
   * **Framing.** The helper's stdout is one JSON object per line: `started`, `out` and `err` (base64, `truncated` flag), and `end` (`exit`, `reason` in `exited`, `timeout`, `output_limit`, `oom`, `cancelled`, `start_failed`; `ms`, `peak_mb`, `credential_b64`, byte counts). It reads the unit's stdout and stderr itself on two pipes, counts bytes, flushes every 50 ms or 4 KiB, stops the unit at `stdout_kib` or `stderr_kib` (`output_limit`), has its own run timer plus `RuntimeMaxSec` (the run limit plus 5 seconds, so the helper's timer fires first), and stops the unit when its stdin reaches end of file or its stdout breaks (the dead-man switch).
   * `--stop`: one run id on stdin, regex-checked; only a unit this helper started (it holds a run record) is stopped.
   * `--finish <run-id>` (root, called by `ExecStopPost=+`): writes the unit's memory peak, CPU time and systemd's own result word (`oom-kill`, `timeout` ...) to a root-only handoff file. The `--start` of the same run puts it into the end frame and deletes it.
   * `--sweep` also removes secrets folders, handoff files and run records whose unit `tectac-sbx-<id>` is not active (files younger than 2 minutes are kept, because a run may still be starting), and old canary markers. It keeps removing `selftest-*` folders.
   * The selftest gets a `pipe_streams` row (stdout and stderr arrive on separate pipes through `systemd-run --pipe`, plan section 10 item 1) and `slots_total` in `status.json`. `--status` adds `slots_total`, `slots_used` and the canary result.
3. **The unit builder** (same file). The unit is built from the registry row and Core constants only. Argv and environment values travel as arguments (`--setenv`), never as properties, so a manifest cannot add or change a property. Hardening: dynamic user, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`, `PrivateIPC`, `NoNewPrivileges`, empty capability sets, `SystemCallFilter=@system-service` and `~@privileged @resources`, `RestrictAddressFamilies=AF_INET AF_UNIX`, `RestrictNamespaces`, `MemoryDenyWriteExecute=no` (Node needs its JIT), the `Protect*` kernel and proc properties, `ProtectProc=invisible`, `ProcSubset=pid`, `UMask=0077`, `KillMode=control-group`, `SendSIGKILL`, `MemoryMax`, `MemorySwapMax=0`, `CPUQuota`, `TasksMax`, `LimitNOFILE=1024`, `LimitCORE=0`, `LimitFSIZE` (scratch size), `RuntimeMaxSec`. The file system: `/etc /var /run /opt /srv /mnt /media /home /root` and `/usr/local/lib/tec-tac` are empty read-only tmpfs, with only these bound back read-only: `/etc/ssl/certs`, `/etc/passwd`, `/etc/group`, `/etc/ld.so.cache`, `/etc/resolv.conf`, and when present `/etc/ca-certificates`, `/etc/nsswitch.conf`, `/etc/localtime`, the declared runtime roots, the module's own runner folder and the launcher. A missing required bind refuses the run (`sandbox_unavailable`); nothing leaks. `/work` is a private tmpfs sized from `scratch_mb`.
   * **Network (section 15).** `IPAddressDeny=` is the exact `ADDRESS_DENY` string the selftest proves. At every start the helper reads `/etc/resolv.conf` again and allows exactly the IPv4 resolver that the selftest proved (it answered from inside a filtered unit) and that `resolv.conf` still lists, as `IPAddressAllow=`. None gives `sandbox_unavailable` (fail closed). IPv6 and zone-id resolvers are skipped.
4. **The launcher** (`scripts/sandbox-launcher.py`, installed root-owned 0755 under `/usr/local/lib/tec-tac/sandbox/`, bound read-only into the unit). It runs inside the unit as the unit's own user: prints a nonce header before the runner starts, makes `/work/home`, `/work/tmp` and `/work/out`, runs the runner as a child that shares stdout and stderr, kills the runner's process group if the output pipe closes (a second dead-man switch for a dead helper), and with `--return-credential` sends the refreshed `$SANDBOX_OUT/credential` (regular file, no symlink, at most 16 KiB) as one final line `\n<nonce> CRED <base64>\n`. The nonce lives only in the launcher process, which also turns off its own dumpable flag. The helper takes only that line and strips it, so a forged frame printed by the runner is plain output.
5. **The Django side** (`framwork/tec_tac/sandbox.py`, `sandbox_views.py`). `start()` returns a `RunHandle` (`run_id`, `events(timeout=None)`, `wait()`, `cancel()`, `close()`), `run()` is the blocking form, `cancel(run_id)` stops a run. The first check of each is still `sandbox_disabled`, before any file is read. With the switch on: the caller is verified (AD-26, owner only, else `not_owner`), readiness, the runner and its runtime, input size, parameter and credential names are checked (the helper checks again), one **strict** audit row `sandbox.run.started` is written before the launch (a run that cannot be audited does not start), then `sudo -n /usr/local/sbin/tec-tac-sandbox --start` with the header, input and credentials on stdin only. Audit rows (module `core`, object type `sandbox_run`, never the credential, input or output): started, ended (exit code, reason, duration, bytes, peak memory), refused and cancelled. `status(live=False)` gains `slots_total`, `slots_used` (only with `live=True`: one `sudo --status` call, 3 seconds), `canary_ok` and `canary_at`. New permission group **Sandbox** (`core.sandbox.view`, `core.sandbox.manage`; an effective superuser passes, AD-10) and two routes: `GET /api/tfd/system/sandbox/status/` (view) and `POST /api/tfd/system/sandbox/runs/<run_id>/cancel/` (manage, audited). `openapi.py` groups the two views and the `system/sandbox/` path under "Tec-Tac · Sandbox" (the F11 route-classification tests fail without it). Contract rows, the rule text, `docs/sandbox-capability.md` and `docs/capabilities.md` are updated. The capability stays `core.sandbox` 1.0.0: the changes are additive keys, new routes and permissions, and the launch calls still refuse.
6. **The canary** (`tec-tac-sandbox --selftest --canary`, root only, never in the sudo rule). An in-memory runner `core.canary` (owner `core`, small limits under the ceilings, credential file `auth`, `credential_return`) runs through the same `launch` as `--start`; only the kill-switch constant is bypassed, on the root-only `--canary-launch` path used for the kill tests. Nothing is written to the registry, and a registry row can never claim the canary's owner id. `scripts/sandbox-canary-runner.py` (installed root-owned under `.../canary/`) runs the attacks inside the unit and prints `CANARYROW` lines. The helper never trusts them: it reads a tag, decides the verdict, treats an unknown word as `NOT RUN` and a missing line as `NOT RUN`. Rows: files (planted random 0644 markers in `/etc /var /opt /srv /mnt /media /home /root`, the Tactical and Tec-Tac config folders, `/rmm`, plus the real `local_settings.py` and config files, and another run's `/work`), sockets, loopback (every port in `ss -ltn`, and every listening port on the allowed resolver's address except DNS), LAN (gateway, the private ranges, cloud metadata), DNS (the allowed resolver answers, other resolvers are dropped), public TCP 443 (`SKIPPED`, never a pass, when there is no route), privilege (setuid, ptrace, mount, unshare, mknod, raw socket, `/proc/sys`, module load), writes, processes, limits (memory gives `oom`, fork bomb stopped by `TasksMax`, loop gives `timeout`, scratch size, stdout cap gives `output_limit`), abstract sockets (a reachable one is a Medium finding, plan R1), credentials (only under `$CREDENTIALS_DIRECTORY`, mode, not in the environment, not in `ps`, `/proc/*/cmdline`, `systemctl show` or journald, nothing left in the secrets folder, the `credential_return` round trip, the frame stripped from the output), cancel (stop mid-run, SIGKILL the helper, close the caller's stdin: the unit is gone within 5 seconds, nothing left), concurrency (3 starts on 2 slots give 2 runs and 1 `busy`; the per-person limit holds) and latency (50 no-op runs, p50 and p95 against 400 ms, a `WARN`, not a failure). The planted markers are removed in `finally` and by the sweep. `CANARY PASSED` only when no row is `ATTACK SUCCEEDED` or `NOT RUN`. It writes `/var/lib/tec-tac/sandbox/canary.json` (root 0644: counts and failing rows, no secret), which `status()` reports as `canary_ok` and `canary_at`.

## Module-facing changes

**None uses `core.sandbox` yet.** A search of `modules/` finds no `core.sandbox`, `sandbox_runners`, `sandbox.register`, `tec_tac.sandbox`, `tec-tac-sandbox` or `runtime_roots`, so no module is affected and no compatibility path is needed.

* `status()` gains four keys (`slots_total`, `slots_used`, `canary_ok`, `canary_at`) and a `live` argument. Read the keys you know and ignore the rest.
* `start()` returns a `RunHandle` and `run()` returns a result dictionary. While the switch is off both still raise `SandboxError` `sandbox_disabled` before reading anything, so code written against 1.17.116 behaves the same.
* What ai gets later, when the switch patch is signed: `start`/`run` for its own runners, with credentials in and the refreshed credential back (`credentials_out`), a stream of output events, a hard stop (`cancel`, `close`), and the error codes `busy` and `person_busy` with `retry_after`. ai passes the signed-in `user` so the per-person limit means something.
* Two new permission codes, `core.sandbox.view` and `core.sandbox.manage`, appear in the role editor under **Sandbox**. Nothing grants them automatically.

## Where the plan was wrong, and what I did

1. **Credential return needs an in-unit launcher.** The plan has the root `--finish` read `SANDBOX_OUT` from the unit's `/work` tmpfs. A `+` `ExecStopPost` runs outside the unit's mount namespace and cannot see it. I built the small Core-owned launcher (item 4) instead. It runs as the unit's own unprivileged user, so it widens nothing.
2. **The routes sit under `system/`, not `core/`.** Every Core system route is under `system/` and Core has no `core/` route prefix. The status route is `/api/tfd/system/sandbox/status/`. Nothing in `modules/` uses either path.
3. **`/etc/resolv.conf` has to be bound.** The plan's bind list leaves it out. With `/etc` hidden, a run would not find its resolver and would fall back to `127.0.0.1:53`, which the filter blocks. Allowing the proven resolver by address only helps if the run can read where it is, so `/etc/resolv.conf` is a required read-only bind.
4. **`/work` is mode 1777, not 0700.** A tmpfs from `TemporaryFileSystem=` is owned by root, so a 0700 mount would be unwritable for the dynamic user. `/work` is private to the unit's mount namespace, so the open mode shows nothing to another run. The launcher makes `home`, `tmp` and `out` 0700 inside it. **Verify on dev02** (the canary's first run shows it at once as `start_failed`).
5. **`/usr/local/lib/tec-tac` is hidden too.** Without it a run could read every module's registered program and the registry. The module's own runner folder and the launcher are bound back.
6. **The caller keeps stdin open.** The plan has the caller close stdin after the input. I made the stdin of `--start` the liveness line instead: the caller keeps it open until the run ends, and the helper stops the unit on end of file (and on a broken stdout pipe). Closing the handle is therefore the dead-man switch. A silent run is noticed at once, not at the next output.
7. **`wait()` returns the reason; it does not raise.** The plan lists `timeout`, `output_limit`, `oom` and `cancelled` as `SandboxError` codes and as `reason` values. A caller that wants the partial output of a run that hit its cap needs the result, so `wait()` and `run()` return it with `reason`, and `wait(raise_on_failure=True)` raises the matching `SandboxError`. Start-time refusals (`busy`, `runtime_unverified` and the rest) raise from `start()` as the plan says.
8. **`start()` returns after the run has started.** It waits for the helper's first frame (the queue wait, at most `queue_seconds` plus a short margin). This is what lets `busy` and `person_busy` raise from `start()`.
9. **The sudo child gets `PATH` only, not an empty environment.** `env={}` makes the program lookup fall back to a default path. `PATH` carries no secret.
10. **A module's `cancel(run_id)` works only for a run its own process started.** A uWSGI worker or Celery process that did not start the run cannot prove the run is its module's. Such a call gives `not_owner` (fail closed). The route (`core.sandbox.manage`) can stop any run by id.
11. **Not built: copying the helper's registered and removed rows into Core's audit log.** The helper's log is mode 0640 root, which the Tactical account cannot read, and Core has nowhere to keep a read position. Both are needed. It is a later patch, and the helper's own append-only log still holds those rows.

## Assumptions (information, in `reviews/questions/core.md`, Core 1.17.118)

1. DNS by address (the Patch 1 selftest proved it). The canary tries every listening port on the resolver's address and fails on any non-DNS answer.
2. No IPv6 (`AF_INET AF_UNIX`). An IPv6-only resolver makes the sandbox not ready.
3. The in-unit launcher for credential return.
4. The kill switch stays `False`; the canary uses a root-only path.
5. The system/ route prefix.
6. Slots and the person, as the plan says. `requested_by` is not verified by Core.
