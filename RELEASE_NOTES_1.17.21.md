# Tec-Tac Framework 1.17.21

This release does three things. A provider module can now ask Core which module's code is calling it. Core writes an audit row when it refuses a change before Tactical is called. A create operation can name the object it made.

Capabilities: `core.caller_identity` is new at 1.0.0. `core.tactical_operations` goes from 1.6.0 to 1.7.0. It is still major 1. Everything below is additive.

## Module-facing changes

Each change below needs `requires.framework >=1.17.21` in a module that relies on it. Nothing that was accepted before is refused. No module under `modules/` uses `calling_module` yet.

| **`tec_tac.caller_identity.calling_module(*, provider_module_id)`** returns a frozen `CallerIdentity(module_id, kind, module_version)` or `None`. `kind` is always `module`: the identity names signed modules only, and Core is never a caller (AD-26). Nothing is passed in by the caller. Core walks the Python stack from the code that called it. That frame must be the provider's own, and the provider's frames that follow one another directly are skipped. The first frame after them is the caller, and only that frame. ## What changed and why

**Caller identity.** A caller used to name itself in an argument or a context dict, and nothing checked the name. A provider such as `globalsettings.email` could not tell one module's call from another's. Now the provider asks Core, and the caller passes nothing. Core reads the answer from the call itself. The check reads the enabled state each time, so a module switched off a moment ago is refused at once. A frame that belongs to a disabled module stops the walk. A disabled module cannot hide behind an enabled one above it. We did not add a cache of the module list. A module that was installed a moment ago must be seen, and a stale list could name the wrong module.

**The refusal row.** Core already wrote a row when Tactical refused a change. It did not write one when Core refused it first. A module that dropped its own failed row, as AD-19 now says, could leave an attempt with no row at all. Now every refused change has exactly one row, whoever refused it. The row carries nothing the caller typed. The error text sent back to the caller is unchanged.

**The create row.** A create has no id in the path, so its row had a null object id. A reviewer could not tell which script or check was made. The success row now names it. A refused row still does not, because a refused attempt must not confirm that the object exists, and the text can come from the request or from Tactical.

## Not in this release

- Core's own Priority 1 notice email through `globalsettings.email`. Caller identity no longer names Core (AD-26 condition 2), so Core cannot reach that provider through `calling_module`. Core keeps sending the email through its own SMTP path (`send_p1_email`, as in 1.17.15). A separate Core-internal path comes in a later release.
- Checking the claimed module id inside `notices.publish` and `build_operation_context`. Refusing a mismatch would break modules that are accepted today. `core.caller_identity` is the building block for an opt-in check in a later release.
- A row for the other validation refusals (`body_too_large`, `invalid_query`, the upload codes, a changed route). Not asked for, and modules such as reportmanager write their own row for some of them. CQ69.
- The create-row object id on refusal rows. CQ70.
- The runtime setting for a private-network mail relay, hand registrations that survive uninstall, the held Medium from the 1.17.16 review and the other held Lows.
- The next public contract export: it is generated on the dev server after 1.17.21 is installed.

## Fixed after review

Round 1 blocked 1.17.21 on one item.

- **A callback a module registers was identified as Core when Core ran it.** The 1.17.21 walk called the first frame under `tec_tac` Core. A module could register a provider's function, or a `functools.partial` of it, as a Scheduler handler or a Tactical row lookup. Core's executor then made the call, and the provider saw Core. Now a frame counts as Core only when its code is on a fixed entry list that Core builds itself: the Priority 1 notice sender, `module_failure_notices.send_p1_email`. Any other `tec_tac` frame (the Scheduler executor, the row-lookup call, signal dispatch) stops the walk and gives `None`. No module can add to the list. If the list cannot be built, nothing is Core.
- Module-facing: `calling_module` returns `None` where 1.17.21 returned Core for a callable Core ran for a module. Nothing in `modules/` called it yet. The `limits` text, the docstring, the contract row and `docs/caller-identity.md` now say this. Capability `core.caller_identity` stays 1.0.0 (the contract was unreleased).
- Test: `tests/caller-identity-1.17.21.py` now covers the partial as a Scheduler handler, the provider function as a row lookup, the other-Core-frame case and the allow-listed Priority 1 path.

Round 2 blocked 1.17.21-1 on one item.

- **The only trusted Core entry ran caller-supplied callables, so a module could be identified as Core.** 1.17.21-1 trusted `module_failure_notices.send_p1_email`. That function runs the `send`, `have` and `mark` callables it is given, and any module can call it. A module could pass a provider function through one of them, and the provider saw Core. Now the trusted entry is a private function, `module_failure_notices._deliver_p1_via_provider(job_id)`. It takes only a job id, loads the notice and the recipients itself, and has no callable seam. `calling_module` accepts it only when the frame that called it is `sweep_failed_jobs`, and only when both frames run in `module_failure_notices`' own globals. The code objects are captured once when `caller_identity` is imported and compared by identity, so rebinding `send_p1_email` or the entry name in `module_failure_notices` to a module function does not make that function Core. `send_p1_email` and everything it calls are now plain Core frames that give `None`.
- Nothing calls `_deliver_p1_via_provider` yet. Core does not call `globalsettings.email` until that provider ships, so today `calling_module` never answers Core. The entry is the one place that call will be made from, in its own frame.
- Module-facing: no change for any module. `calling_module` is as unreleased as before (nothing in `modules/` calls it). The docstring, the `limits` text, the contract row and `docs/caller-identity.md` name the new entry.
- Tests: `tests/caller-identity-1.17.21.py` now runs the real `module_failure_notices.send_p1_email` from a module file with the provider function as `send=functools.partial(...)`, as `have=`, as `mark=`, and called directly. Each gives `None`. It also checks that rebinding `send_p1_email` or the entry to a module function gives the module, not Core, that the entry called from a module file or another Core function is not Core, and that a copy of the entry compiled into other globals is not Core.

Round 3 blocked 1.17.21-2 on one item, with one Medium and one Low fixed in the same rebuild. Johan decided on 11 October 2026 to drop Core as a caller (AD-26 condition 2).

- **Any module could be identified as Core through `sweep_failed_jobs`' seams and a frameless callable (HIGH).** The trusted entry `_deliver_p1_via_provider` could be reached from the real sweep frame by passing it as `recipients_for`, then a rebound `send_p1_email` (a `functools.partial` or an `eval` lambda, which leave no module frame) reached the provider and the walk answered Core. The Core caller special case is now gone: `_capture_core_entries`, `_is_core_entry`, `KIND_CORE`, `CORE_MODULE_ID` and every path that built `CallerIdentity("core", ...)` are removed, and `_deliver_p1_via_provider` is removed from `module_failure_notices` (nothing called it; the file is back to its 1.17.20 content). No frame, entry or path answers Core.
- **Generated frames and skipped gaps could borrow another module's identity (MEDIUM).** The walk skipped `<...>` frames and library frames and went on to a module further up, so a module could register an `eval` lambda or a partial with another module's callback and be seen as that module. Now only the first frame after the provider's own frames counts. A generated frame, a library frame, a Core frame or any other gap there answers `None`. The frame that calls `calling_module` must also be the provider's own. The callback-surface limit is added to `LIMITS`, `docs/caller-identity.md` and the contract row.
- **A JSON parse error after Tactical applied a change could drop the success row (LOW).** `run_tactical_operation` now catches any exception around the parse of Tactical's answer (a deeply nested answer raises `RecursionError`) and keeps the raw answer, so the audit row is always written.
- Module-facing: `kind` is always `module`; the metadata lists `kinds: ["module"]` and `core_is_caller: false`. A provider whose function is reached through a decorator, a library call or generated code now gets `None`. Nothing in `modules/` calls `calling_module` yet. Capability `core.caller_identity` stays 1.0.0 (the contract is unreleased).
- Tests: `tests/caller-identity-1.17.21.py` now runs, from a module file, the real `sweep_failed_jobs` with `send_p1_email` rebound to `functools.partial(provider_fn)` and to an `eval` lambda, and with each of `recipients_for`, `publish`, `existing`, `mail_settings`, `email_have`, `send_mail` and `mark_sent` set to a partial of the provider function and to an `eval` lambda. Each answers `None`. It also covers a module's handler, partial and eval lambda run by a Core executor, `<string>` and standard-library frames between the module and the provider, a library frame inside the provider, `calling_module` not called by the provider, and it records every identity built during the run and checks none is kind `core`. `tests/tactical-operations-object-field-1.17.21.py` covers `RecursionError` and `MemoryError` during the parse.
