# Tec-Tac Framework 1.17.96

Date: 30 October 2026. Core starts faster, the installer waits long enough for its own checks, a rollback no longer fails on one of those checks, and lifecycle job logs show 200 lines.

Closes: the dev02 start-up profile of 30 October 2026 (Django start-up 46.1 s, 122 plugin discoveries), the failed Core 1.17.95 update on dev02 (the contract catalog check ran past the old 45 s limit), and Johan's two requests of 30 October 2026 (rollback must not fail on a verification step; 200 log lines).

## What changed and why

1. **Plugin discovery is cached per process (`tec_tac.registry`).** One `get_plugins()` call read every `tec_tac.json` and checked it again, about 70 ms, and start-up made 122 such calls (10 614 manifest loads). Now `discover_plugins()` (no arguments), `get_plugins()` and `get_plugin()` reuse the validated, frozen `PluginSpec` tuple until a fingerprint of both roots changes. The fingerprint is checked on every call: no time window. It covers the root and module folders, each manifest (mode, mtime, ctime, size, inode) and the extra paths a manifest depends on (`python_paths` other than the module root, `server_maintenance_actions` executables). `get_plugin()` answers from an index built once, with the same errors (not found, and the multiple-types error). `discover_plugins(extensions_root, reportsets_root)` with explicit roots (module staging) is never cached.
   * **Fail closed.** A `RegistryError`, `OSError` or fingerprint read error is raised or bypasses the cache and is never stored. A validation error (duplicate Django app or permission) is raised on every call. A file changed within 2 seconds of the read is not trusted (a same-size rewrite inside one timestamp tick), and nothing is stored if the files changed during the read.
   * **Cross-process.** The root helper changes module files in another process, so the fingerprint is the guard. New `registry.invalidate_plugin_cache()` also clears this process at once. It is called from `module_manager._dispatch`, `module_manager_v2._dispatch_v2` (install, upgrade, replace, bundle install, enable, disable, visibility, remove), `module_hotfix._dispatch` (apply, rollback), `module_state.save_state` and `module_state.forget_module`. A `threading.RLock` guards the cache.
   * **Start-up.** `bootstrap.load_extensions`, `reporting.settle_reporting_bridge`, `route_mounting._mount`, `capability_status` / `_provider_module_status`, `rbac`, `module_runtime`, `notices`, `openapi`, `views`, `audit` and the direct `discover_plugins()` users (`caller_identity`, `event_jobs`, `system_actions`, `module_dependants`, `endpoint_transport`, `server_job_hooks`, `scheduler`) all call `get_plugins`, `get_plugin` or `discover_plugins()`, so start-up discovers once per process. No other repeated walk was found, so `bootstrap.py` is unchanged. `scheduler._manifest_signature` is left as it is.
   * **Timing here.** `tests/plugin-discovery-cache-1.17.96.py` times 122 `get_plugins` calls over 53 generated manifests (26 extensions, 26 reportsets, one with a nested python path and a server-maintenance executable): **uncached 49.097 s, cached 3.643 s** (Windows, ~0.4 s per uncached call, so far slower than Linux). The cached figure includes the first read. **The effect on the dev02 Django start-up (46.1 s) cannot be measured on this PC (Django is not installed).** The count is exact: one manifest load per manifest for 122 `get_plugins` and 120 `get_plugin` calls, where before each call loaded all of them. `capability_status` (87 calls in the profile) goes through `get_plugin`; it could not be driven directly here because `module_state` needs `fcntl`, so the 120 `get_plugin` calls stand in for it.
2. **Installer verification limit 120 s with a clear failure log (Johan, 30 October 2026).** All 13 `timeout 45s` verification steps in `install.sh` (12 fatal, the saved views repair stays a warning) now go through one function `run_verify_step <label> <code>` and one constant `VERIFY_STEP_TIMEOUT_SECONDS=120`. On a failure the log names the step, the elapsed seconds, the exit status (124 is reported as "timed out after 120 s") and the last 20 lines of the step's output with passwords, secrets, tokens, keys, authorization text and URI passwords masked. No step is removed or weakened; every old message is kept. `scripts/system-update-helper.py` `VERIFY_TIMEOUT_SECONDS` goes from 90 to 120 because its own check runs the same contract catalog step. `INSTALL_TIMEOUT_SECONDS` (1800) is unchanged. The 1.17.95 to 1.17.96 update runs the new `install.sh`, so 120 s applies at once. A rollback to 1.17.95 runs the old installer with 45 s (see 3).
3. **A rollback does not fail on a verification step (Johan, 30 October 2026).** A fatal verification step now exits **79** (`INSTALL_VERIFY_FAILED_EXIT`) after the usual `[TEC-TAC] ERROR:` line and a `[TEC-TAC-INSTALL] VERIFY-FAILED: Verifying <step>` line. In the update helper, when the rollback installer fails at such a step and the restore, `verify_dynamic_plugins` and the layout check passed, the job gets `rollback: {performed: true, status: "warning", version, warning: <step>, installer_exit_status, advice}`, stage `rolled-back` and the log line `restored <old>, verification warning: <step>`; no `ROLLBACK FAILED`. The job stays `status: failed` with the forward error. The previous version's installer (exit 1) is recognised from its last `[TEC-TAC] ERROR:` line written during the rollback, only for the 12 known steps. Anything else (a failing restore, another status or error text, a failing check after the installer) stays `status: failed`, stage `rollback-failed`. A failed restore has no `installer_exit_status`. `system_update_audit` writes "`<old>` was restored; the check after the restore reported a warning, check the server." and `rollback_status: warning`. **Takes effect from the update after 1.17.96 is installed**, because the helper that runs a rollback is the one already installed.
4. **Lifecycle log tail is 200 lines.** New `module_job_logs.tail_lines(path, max_lines=200, max_line_chars=2000)` reads only the last 512 KiB, drops a partial first line, cuts each line at 2000 characters, and returns `[]` for a missing or unreadable log. `module_manager.public_job` (was 40), `module_hotfix.public_hotfix_job` (was 40) and `system_update.public_job` (was 80) use it, so the single-job routes (module job start/status, v2 install and upgrade jobs, hotfix jobs, system update detail and recent history) return 200. The old list `GET /api/tfd/modules/v2/jobs/` (up to 1000 rows, each with `log_tail`) keeps 40 per row (`HISTORY_ROW_LOG_TAIL_LINES`) so the payload does not grow five-fold. Rows without log text are unchanged. The text is still not scrubbed in `log_tail`. `server_backup._safe_log_tail` is unchanged. The `.job-log` box scrolls, so the UI needs no change for 200 lines.
5. **Text.** `contracts.py` (system update job row: `rollback` object and the status `warning`, the audit message note, the 200-line `log_tail`), `docs/system-update-signed-releases.md`, `docs/module-job-logs.md`, `docs/system-update-logs.md` and the new `docs/plugin-registry-cache.md`.

## Module-facing changes

* None breaking. No capability, contract signature or import changes. `reportmanager` (`get_plugin`) and `serverhealth` (`get_plugins`) get the same results faster. Extra optional keyword on `module_manager.public_job` only. Backups uses `server_backup` log tails, unchanged.
* A module that rewrites its own manifest in the same process and reads the registry again within 2 seconds sees the new file (the racy-window rule reads it again).
* **Additive for readers of the system update job:** `rollback.status` can now be `warning` (with `warning`, `installer_exit_status`, `advice`). The UI half is a request in `reviews/requests/ui.md` ("System updates view (Core 1.17.96)").
